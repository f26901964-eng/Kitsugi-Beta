# Manga-TR integration notes

Compared against Manga-TR source at Kitsugi-Manga-Plugins PR #6 commits `261dd212` (v25) and `245c305f` (v26). This is an application-side integration, not a change to the extension.

- Chapters are distinct by URL, retain scanlator metadata, and the visible chapter query matches name/number/scanlator. The extension performs its own offset-based load-more requests; the host does not try to reproduce the web UI. Same-manga detail and chapter updates are serialized because KeiSource rejects concurrent updates for the same URL.
- Search/popular/filters pass page numbers through to the extension and respect `hasNextPage`. Select options use the actual extension filter indices and values; no hard-coded server parameter mapping is made in the host.
- Page images use `HttpSource.getImage` and its own client/interceptor chain. The full image URL including its fragment is the cache key. The reader displays the resulting local processed file, not the URL through Coil's network client or a WebView. Manga-TR's CDN requests get a referer and its hosts default to identity encoding; its extension's challenge and DDoS interceptors remain in charge.
- Membership-required page errors offer a login WebView and synchronization through Android's CookieManager. Live-site authentication and cookie domain behaviour must be tested on device. Website library management, notification, and tracking actions are not exposed by the inspected extension Source API and are not implemented as site actions here.
- The app offers native LTR/RTL paged, vertical paged and continuous webtoon reading. These are not identical to the website's named Tümünü/Sayfadan/Webtoon controls.

## Published APK discrepancy

At the initial inspection, `builds/index.json` advertised Manga-TR **1.6.26 / 106026**, but `builds/apk/tachiyomi-tr.mangatr-v1.6.26.apk` declared **1.6.24 / 106024** in its manifest and was byte-identical to the published v24 APK. Both SHA-256 values were `1392f9f4e9cc52b23bf018a394ae94a0f0fe19249bd65ac69f2266b3b81687a8`. PR #6's v26 APK had the same mismatch. The checked-in v25/v26 source therefore does not prove those features are in the downloadable APK. A later successful publication corrected this discrepancy: at builds commit `bca61cbff15930394f3c87fac9ce556b041c7bac`, the downloaded APK declares 1.6.26 / 106026 and has SHA-256 `17694bbcbb7ade8e9a03fcd60c3ce4fb24633b0312a5e82a5ddee9bfc83360f9`. Its behavior still requires device testing. The installer checks Mihon APK package/version metadata against the index and leaves the installed file intact when they differ.

## Search failures and release compatibility

The published APK's `classes3.dex` contains KeiSource's runtime check requiring the host interceptor simple name `CloudflareInterceptor` (alongside `UncaughtExceptionInterceptor` and `UserAgentInterceptor`). The prior release rules did not keep the Kitsugi interceptor name, while release builds enable R8. If R8 renames it, KeiSource fails before issuing a request with `CloudflareInterceptor must be present in default client`. The old failure classifier can mistake that host error for a captcha because its message contains `Cloudflare`; the screenshot alone cannot prove which underlying error occurred on a device. The release rule now keeps the class, and this specific error is not categorized as a site captcha.

Search errors now show their source and actual message instead of presenting failures as empty results. Explicit retry uses failed sources even if the automatic search coordinator put them in cooldown. The source interceptor check and linkage-error reporting have Android instrumentation coverage; they still need running against the minified release app and the real site.

### Additional checks and emulator regression

The published v24 APK was also inspected at DEX method-descriptor level. All 27 references to the host's manga model methods and constructors were matched against JVM signatures compiled from the host model sources with lightweight dependency stubs. The corrected v26 APK has 30 such references; 29 matched directly and `Filter.Select.getState` resolves to the inherited `Filter.getState`. This is not a complete ABI or Android runtime verification. The APK and current extension source depend on newer Kotlin/coroutines/serialization APIs than some host declarations; their actual resolved versions and R8 behavior require Android testing.

The `Manga-TR Android integration` workflow downloads the v24 and v26 APKs at fixed commits, verifies their SHA-256 values, and runs Android 14 emulator instrumentation. `MangaTrPublishedApkTest` loads both real DEX files through the host class loader and tests filters, search, detail, chapters, pages and image retrieval using deterministic fixture responses. `MihonMangaIntegrationTest` separately checks source-transformed fragment URLs, cache behavior and error reporting with a fake source. The fixture test does not exercise the live site, and the workflow must actually pass before counting it as evidence.

Speculative automatic mirror probing is disabled for the Manga-TR package: a merely reachable guessed domain is not proof it belongs to the site. Existing explicitly configured domains are retained, so an old automatically selected domain should be checked/reset by the user if requests go to an unexpected host. Image-path linkage errors are reported as source errors rather than silently leaving a reader operation running.

Manga-TR's inspected v24 APK source and current source create a new details `SManga` without setting its `url` in `fetchMangaUpdate`. Since the host implementation uses a `lateinit` URL, blindly mapping this object would throw `UninitializedPropertyAccessException`. For the details response only, the bridge now falls back to the exact URL requested if the returned URL is absent or blank. Both the fake-source test and the pinned APK test cover this case; they have not yet been confirmed on a device.

The cookie jar now matches each cookie by its own domain, host-only flag, path and secure flag, rather than by the host that supplied the response. Domain cookies received from a forum subdomain can therefore be sent to the main site when permitted; host-only cookies cannot. Same-name cookies at different paths remain distinct. An Android instrumentation test covers these semantics, and a small JVM stub harness passed for replacement, deletion and persistence; actual Manga-TR login/cookie behavior still needs a live device test.

Install/update attempts now save the previous APK before replacement and restore it and the previously loaded source if download, user trust, or class loading fails. The backup is on the same filesystem; a failed rollback is logged and retains the backup rather than silently deleting it. The user-approved signing fingerprint is compared with the re-downloaded file, rather than automatically trusting a changed signature. This transaction does not yet provide crash-recovery across process termination; a plugin that loads successfully but fails only during later site requests is also not automatically rolled back. Two filesystem rollback tests passed using a local JVM harness; Android install/update behavior still needs instrumentation/device testing.

GitHub Android build run `41893534294`, at application commit `d6c4802`, completed successfully: selected Gradle unit tests (including the Manga tests), FOSS debug and minified release APK assembly, and DEX verification all passed. The verifier reported 0 VerifyErrors in both APKs. This establishes compilation and DEX structural validity for that commit, not actual plugin execution, a live-site result, or a guarantee for subsequent code changes.

For WebView synchronization, Android only exposes cookie name/value pairs, not the original Domain attribute. The bridge therefore imports each visible cookie as host-only for the URL queried, rather than accidentally widening an unknown host-only cookie to subdomains. The forum and main host are synchronized separately; real login behavior still requires device validation.
